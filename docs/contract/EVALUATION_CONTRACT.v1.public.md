# PRESAGE — Precommitted Real-Data Evaluation Contract

**Status: RATIFIED AND FROZEN 2026-08-24, before any real-data evaluation run.**
**Run trigger: ≥ 30 TEST events (approximately ≥ 75 total). Primary test runs
ONCE. No interim look.**

This document exists so the rules cannot move once the answer is visible. It is
written while the outcome is unknown and it is binding on the outcome whatever
it turns out to be.

Nothing in it may be edited after the primary run. If something in it is wrong,
the correction is a *new*, separately versioned contract with its own
pre-registered run — never an edit to this one. Any edit after the freeze
invalidates the pre-registration and the run must be reported as exploratory.

**Freeze procedure.** The SHA-256 of this file was computed at ratification and
written to `results/CONTRACT_HASH.txt`. The run manifest must cite that digest.
Before the primary run, recompute `sha256sum results/EVALUATION_CONTRACT.md` and
compare. **A run whose manifest cites a digest that does not match the contract
file on disk is not a pre-registered run and must be reported as exploratory** —
that mismatch is the only tamper-evidence this scheme has, so it is checked, not
assumed.

## 0. Standing rules

### 0.1 Nothing in the synthetic prototype is evidence

**Nothing in `prototype/` is evidence about real markets.** Not the forward
probability field, not the horizon views, not the gates, evolution or replay
pages, not the coverage numbers those pages print, and not the CRPS
demonstrations in `prototype/edge_semantics.py`.

Every number that appears in `prototype/` was produced from synthetic series
generated by `makeHistory()` and from analytic densities generated by
`field()`. The replay page reports aggregate band coverage; that number
describes a synthetic series and a deliberately crude forecaster and describes
nothing else. The prototype exists to settle **encoding and semantics** — what a
claim would look like if we had one, and which claims the visual grammar is
permitted to make. It settles nothing about whether the claim is true.

The prototype is frozen as of this document. No result in it may be cited in any
real-data report, in any direction, including as a sanity check.

### 0.2 Why the threshold is where it is

Someone may eventually pay for this, and a claim sold on an underpowered result
is the seller's fault, not the buyer's.

That is the whole reason the sample threshold, the single-run budget and the
outcome states are fixed in advance rather than negotiated against the answer.
Every rule in this document that costs us power or delays the run is paying for
that sentence.

### 1.6 The predictive model — locked model class

The existing edge harness in the frozen research implementation scores *separation* (AUC, Cohen's
d). CRPS scores a *predictive distribution*, which requires a model that emits
one. **No such model exists in the research layer today.** It must be written
before the run, and it is therefore specified here in full so that writing it is
implementation, not a modelling decision made in sight of the answer.

**Locked class: Gaussian location–scale distributional regression with ridge
penalty.**

For each (coin, horizon, model) the predictive distribution at anchor *t* is
N(μ_t, σ_t²) with

```
μ_t      = β₀ + βᵀ x_t
log σ_t  = γ₀ + γᵀ x_t
```

- `x_t` is the standardised feature vector (§1.8).
- Parameters fit by penalised maximum likelihood, ridge penalty λ applied to
  β and γ but not to the intercepts.
- λ selected by **5-fold blocked cross-validation inside the TRAIN partition
  only**, over the fixed grid `λ ∈ {1e-4, 1e-3, 1e-2, 1e-1, 1, 10, 100}`.
  Blocks are contiguous 24-hour spans, so folds do not interleave in time.
  The TEST partition is never touched during selection.
- Optimiser: L-BFGS-B, maximum 500 iterations, initialised at β = γ = 0,
  γ₀ = log(sample sd of the TRAIN target). Non-convergence is a reported
  failure, not a silently accepted fit.
- Identical class, identical λ grid, identical fitting procedure for Model A and
  Model B. **The only difference between A and B is which columns are present.**

Gaussian is chosen because both scoring rules have closed forms under it, which
removes sampling noise from the comparison, and because a fixed simple class
cannot be tuned toward a flattering answer. It is not chosen because returns are
believed Gaussian — they are not, which is exactly why the log-score
tail-calibration diagnostic in §2 is mandatory rather than optional.

### 1.7 Scoring rules — locked formulae

Let z = (y − μ)/σ, Φ the standard normal CDF, φ the standard normal PDF.

**CRPS (primary).** Strictly proper. Closed form under a Gaussian predictive
distribution:

```
CRPS(N(μ,σ), y) = σ · [ z·(2Φ(z) − 1) + 2φ(z) − 1/√π ]
```

**Log score (diagnostic).** Strictly proper, tail-sensitive:

```
LogS(N(μ,σ), y) = ½·log(2πσ²) + z²/2
```

Both are **negatively oriented** — lower is better.

**EDGE, the primary quantity:**

```
EDGE = mean_over_test_anchors[ CRPS_A(t) − CRPS_B(t) ]
```

Positive EDGE means Model B is better. The paired per-anchor difference is the
unit of analysis, which handles the common variation between the two models.

A ratio skill score `1 − mean(CRPS_B)/mean(CRPS_A)` is reported alongside for
interpretability. **The ratio is descriptive only. All inference is on EDGE.**

**Divergence measures are not edge and are not reported as edge.** KL and
Wasserstein between the two predictive distributions measure how *different* the
models are, not how *accurate* either is. A pure-noise feature set moves both.
They may appear in the report only under a heading that says they are
diagnostics of model disagreement.

### 1.8 Data handling — locked

Applied identically to A and B, fitted on TRAIN only, applied unchanged to TEST.

1. **Zero-variance exclusion.** A feature with zero variance on the TRAIN
   partition is dropped, and the drop is reported by name. (This is the rule
   that catches `liq_count`, and the same class of bug that once let a constant
   column score AUC 1.000.)
2. **Missing values.** A feature missing for an anchor is mean-imputed from the
   TRAIN mean, and a per-family missingness rate is reported. An anchor missing
   more than 50% of Model B columns is dropped from **both** models, so A and B
   always score the identical anchor set. Dropped-anchor count is reported.
3. **Standardisation.** Z-scored using TRAIN mean and TRAIN sd.
4. **Winsorisation.** Features clipped to the TRAIN 0.5th / 99.5th percentiles
   before standardisation. Fixed; not tuned.
5. **No target transformation.** The target is the raw forward log return.
6. **Provenance.** Every record carries its profile and contract, per the loader
   guarantee in the frozen research implementation. Silent cross-profile joins remain impossible. A run
   that trips a provenance guard is void, not repaired.

### 1.9 Train / test split — declared now

**Rule (deterministic, fixed here):**

- Order all frozen qualifying events by time, pooled across the included coins.
- `T_split` = the timestamp of the event at the **60th percentile by count**.
- **TRAIN** = every anchor with `t < T_split`.
- **EMBARGO** = anchors in `[T_split, T_split + 24h)` are discarded entirely.
- **TEST** = every anchor with `t ≥ T_split + 24h`.

The 24-hour embargo exists because a 360-minute trailing sigma window plus a
30-minute lead window plus a 30-minute forecast horizon means information near
the boundary is shared between the partitions. Without it, "out-of-sample" would
be false.

`T_split` is computed from the frozen event file **before any variable is
computed**, and is written into the run manifest at that point. Out-of-sample
means the model never saw those events; the manifest is what makes that
checkable rather than asserted.

**Why a rule and not a calendar date.** A fixed date was considered and
rejected: event accrual rate is unknown, and a date chosen now could easily put
almost all events on one side, leaving a partition with no power. The 60/40
count rule guarantees both partitions contain events, is fully deterministic
given the frozen event file, and is fixed before any model sees any feature.
It has all the pre-registration properties of a date and none of the fragility.

### 1.10 Reportability threshold — and what it implies

`MIN_EVENTS_FOR_REPORT = 30` (the frozen reporting implementation), `MIN_EVENTS_FOR_EDGE = 30`
(the frozen research implementation).

**The 30-event minimum applies to the TEST partition, not to the total.** A
primary out-of-sample claim resting on fewer than 30 out-of-sample events is not
reportable by the project's own existing constant.

**Consequence, stated plainly:** with a 60/40 split, the trigger for running the
primary test is **≥ 75 total qualifying events**, not 30. This is a stricter
reading than "≥ 30 events" taken literally. It was raised before the freeze and
**ratified 2026-08-24** (§7.1); the delay it costs is accepted, for the reason
in §0.2.

## 2. What the report shows — every time, flattering or not

The report generator emits **all** of the following on every run. There is no
conditional path that omits an item because it came out badly. An item that
cannot be computed is printed as "not computable" with the reason; it is never
silently absent.

1. **Event count and coverage** — total qualifying events; events per coin; per
   lead bin; TRAIN / EMBARGO / TEST counts; analysed minutes; the fraction of
   wall-clock time with complete band coverage; anchors dropped by §1.8 and why.
2. **Per-coin breakdown** — EDGE, CI, and every §2 quantity, for each coin
   separately.
3. **Per-horizon breakdown** — the same, for H = 5, 15, 30.
4. **Combined result** — the pooled-across-coins result at each horizon,
   presented *alongside* the per-coin table and never instead of it.
5. **Out-of-sample CRPS skill vs baseline, with confidence interval** —
   EDGE with a 95% CI from a **stationary block bootstrap** on the paired
   per-anchor CRPS differences: mean block length **120 minutes**, **10,000**
   resamples, seed recorded in the manifest. The block bootstrap is used because
   overlapping feature windows make adjacent anchors dependent and an i.i.d.
   bootstrap would produce a CI that is far too narrow.
6. **Log score as a tail-calibration diagnostic** — mean log score for A and B
   on the same TEST anchors. **If the log score and CRPS disagree in sign, that
   is reported prominently as evidence of miscalibrated tails**, and the run is
   marked SUSPICIOUS per §3. A model can improve CRPS (which weights the bulk)
   while degrading the log score (which punishes confident tail errors); that
   pattern means the σ_t model is wrong, and it must not be presented as a win.
7. **BH-adjusted significance across all tests run** — per §5. The raw p, the
   BH q, the family the test belongs to, and the family size are printed for
   every test, including the ones that fail.
8. **Precision vs base rate with the coverage-matched chance floor** — using
   the matched chance-floor routine, not the global point-alert floor. The
   global floor is not reported as if it were the bar; it made an always-on
   noise signal look excellent, which is why the matched floor exists.
   `REPORTABLE_MIN_PRECISION_LIFT = 0.10` absolute percentage points.
9. **False alerts per day** — absolute count and rate, per coin, at the declared
   alert threshold. Recall is reported next to it; neither is reported alone.
10. **Placebo results** — hour-matched placebo, same machinery as the archive
    pipeline, with the number of draws and the resulting p.
11. **Matched-control quality** — how well hour-matched controls actually match
    on the matching covariates, with the residual imbalance. A result on badly
    matched controls is not a result, and the report must make that checkable.
12. **Current sensitivity floor from a fresh meta-test run at the actual event
    count** — `tools/meta-test-guards.py` re-run at the realised TEST event
    count and the realised control count. **The stale figure must not be
    quoted.** For the record, the last measured floor was
    `sensitivity_floor_d = 2.0` at `n_events = 6` — that number describes a
    six-event run in August 2026 and is not the floor for any other run.
13. **Empty and dropped variables** — every feature excluded by §1.8, by name
    and family, with the reason.
14. **Run manifest** — contract SHA-256, code commit, dataset snapshot
    identifier, `T_split`, RNG seeds, library versions, wall-clock start/end.

## 3. Outcome states — decided now

Exactly one of these is assigned to the primary result. The assignment follows
mechanically from the numbers; it is not a judgement call made afterwards.

### SURVIVES

**All** of the following, on the **primary combined model at H = 5**:

1. Reportable sample: **≥ 30 events in the TEST partition**
   (`MIN_EVENTS_FOR_REPORT`).
2. Out-of-sample **EDGE > 0** with a **95% CI excluding zero** (block bootstrap,
   §2.5).
3. **Survives BH** within its declared family (§5).
4. **Beats placebo** — hour-matched placebo p < 0.05.
5. **Precision exceeds the coverage-matched chance floor by ≥ 0.10** absolute
   (`REPORTABLE_MIN_PRECISION_LIFT`).
6. **Holds on the held-out split** — the sign and reportability of the result
   are the same on TEST as the TRAIN-fitted expectation; a result that reverses
   sign out of sample does not survive on the strength of its in-sample value.

Failing **any** one of these is not SURVIVES. There is no partial credit and no
"survives with caveats".

### INCONCLUSIVE

Either:

- TEST partition holds **fewer than 30 events**; or
- the observed effect is **below the measured sensitivity floor** from the fresh
  meta-test at the realised event count — i.e. the harness demonstrably could
  not have detected an effect this size, so the absence of detection carries no
  information.

An INCONCLUSIVE report **must state**:
- the measured sensitivity floor (as Cohen's d and as CRPS-difference units),
- the realised TEST event count,
- **the event count that would resolve it**, computed from the meta-test's
  detection-rate curve at the observed effect size,
- the expected wall-clock date that count arrives at the observed accrual rate.

"Not enough data" without those four numbers is not an acceptable report.

### FAILS

A reportable sample exists (TEST ≥ 30 events) and there is no useful improvement
over the baseline: EDGE ≤ 0, or the CI includes zero, or the precision lift is
below 0.10.

**This is a real, publishable result and is written up to the same standard as
SURVIVES** — same report sections, same completeness, same prominence, no
softening language, no "promising direction" framing, no invitation to try
again with more features. A well-powered null on whether order-book internals
lead 4-sigma moves is a genuine finding about this market and this feature set.

### SUSPICIOUS

An apparent improvement that fails any placebo, control, or robustness check.
Specifically, any of:

- EDGE > 0 with CI excluding zero, but the **placebo also shows** an effect at
  p < 0.05;
- **CRPS and log score disagree in sign** (§2.6) — the improvement is bulk-only
  and the tails are miscalibrated;
- control matching quality is outside its declared tolerance;
- the result is carried by a feature that §1.8 flagged as degenerate;
- per-coin results are wildly heterogeneous in sign while the pooled result is
  significant;
- the result does not reproduce on a re-run **of the identical frozen snapshot**
  with a different RNG seed.

**SUSPICIOUS is treated as FAILS for every decision purpose.** It is never
reported as a positive result pending investigation. The investigation is
reported separately and does not change the decision status of the run.

## 4. If only one feature family survives

This is a live possibility and is defined now, because the temptation to
retrofit "PRESAGE is really about liquidity withdrawal" after seeing which
family won is exactly what pre-registration exists to prevent.

**We must be willing to find that PRESAGE is one narrow signal rather than
"all the internals together."**

### 4.1 How per-family results are reported

Every run reports, at every horizon, for every included coin and pooled:

- the **combined** Model B result (A1 ∪ F1…F9), and
- **nine per-family results**, each being A1 ∪ F_i — the baseline plus that one
  family.

Each family result is presented in the same table as the combined result, with
the same columns (EDGE, CI, BH q, placebo p, precision lift, log-score
agreement). The combined result is never presented alone, and a family result is
never presented alone.

Each family model is fit exactly as §1.6 specifies, with λ re-selected inside
TRAIN for that model. The nesting rule holds throughout: every family model
contains A1, so a family result always means "this family on top of price and
volatility".

### 4.2 BH correction across families

Testing nine families separately multiplies the tests, and the correction says
so. Three declared families of tests, **BH applied within each, α = 0.05**:

| Tier | Tests | Count |
|---|---|---|
| **PRIMARY** | combined model, pooled across coins, 3 horizons | **3** |
| **FAMILY** | 9 feature families × 3 horizons, pooled across coins | **27** |
| **PER-COIN** | combined + 9 families, × 6 coins × 3 horizons | **180** |

BH is applied **within** each tier, and the tier and its size are printed next
to every q-value. Tiers are not pooled into one correction, because they answer
different questions and pooling them would destroy the power of the primary test
to protect exploratory ones. Equally, a tier is never sliced smaller after the
fact to make a q-value shrink — the counts above are fixed by this document.

### 4.3 When a single surviving family counts as SURVIVES on its own

A single family counts as **SURVIVES on its own** only if **all** of:

1. It was pre-registered as one of the nine families in §1.5 — it was; no
   post-hoc regrouping, splitting, or merging of families is permitted, and a
   "family" invented after the run is not a family.
2. It meets **every** SURVIVES criterion in §3 in its own right, at H = 5.
3. It **survives BH within the full 27-test FAMILY tier** — not within a subset,
   not compared against only the families that looked promising.
4. It **holds on the held-out split** with the same sign and reportability.
5. It is **not carried by a single coin** — the family result must be reportable
   in at least half the included coins (≥ 3 of 6) in the PER-COIN tier, or it is
   a lead, not a result.

If it meets 1–4 but fails 5, or fails BH at the 27-test tier, it is a **LEAD**:
recorded, reported, and **requiring its own separately pre-registered test with
its own fresh out-of-sample data**. A lead is never upgraded by re-examining the
data that produced it.

### 4.4 A family surviving while the combined model does not

**This is a FINDING ABOUT THE COMBINED MODEL. It is not a fallback result
reported in place of the combined one.**

The report must state it in those terms: the combined Model B, containing all
twenty-eight declared internals, **failed**; a single family carried signal that
the combined model diluted. That is a statement about feature dilution and about
the ridge model's inability to discard twenty-odd uninformative columns at this
sample size — and it is evidence *against* the "all the internals together"
framing that motivated PRESAGE.

The headline of such a run is: **"Combined model FAILS; F_x is a surviving lead
(or SURVIVES on its own, per §4.3)."** Never: "PRESAGE works, via F_x."

The combined result is always reported first, with its own outcome state,
regardless of how any family performed.

## 5. Run budget

**The primary test may be run ONCE. There is no interim look.**

Rerunning it after more data accumulates is optional stopping, and optional
stopping inflates false positives — an analysis that can be repeated until it
crosses a threshold will eventually cross it whether or not there is anything
there.

Specifically:

- **One execution.** A single run of the primary pipeline against a single
  frozen dataset snapshot, cited by identifier in the manifest.
- **No interim look.** The primary test is not run, peeked at, previewed or
  "sanity checked" on partial data before the threshold is reached. An
  interim look spends the run.
- **The result stands.** Whatever it is. SURVIVES, FAILS, INCONCLUSIVE or
  SUSPICIOUS is assigned once and does not change because more data arrived.
- **No reruns after seeing the answer**, including: re-running with a different
  split, a different λ grid, a different horizon, a different coin set, an added
  feature, a removed feature, or a different bootstrap seed "to check".
- **What is permitted before the run:** implementing §1.6 and §1.7, and
  validating that implementation against **known-answer tests only** — closed
  forms checked against numerical integration, CRPS/log-score checked on
  synthetic Gaussians with known parameters, and the plumbing exercised on
  shuffled-label data where the true answer is "no skill". None of that may
  touch the real TEST partition. A validation run that reads TEST voids the
  pre-registration.
- **Crash-and-fix is not a rerun,** provided no result was observed: if the run
  fails with an exception before emitting any score, the fault may be fixed and
  the run restarted, and both the failure and the fix are recorded in the
  manifest. If any score was observed, it counts as the run.
- **A second look is a new contract.** If a second look is wanted, it is declared
  in advance as a separate pre-registered test, in its own document, with its own
  threshold, its own data window that does not overlap the first, and its own
  outcome states. It is not a rerun of this one, and this contract's α is not
  reused for it.

## 6. After the run

PRESAGE work stops until the event threshold arrives, except recorder health
issues. That is the standing instruction and this document does not change it.

When the threshold arrives, the order of operations is fixed:

1. Verify recorder health and coverage over the whole window.
2. Freeze events to disk; write `_meta.json`.
3. Compute and record `T_split` in the manifest.
4. Re-run `tools/meta-test-guards.py` at the realised event and control counts
   to obtain the **current** sensitivity floor.
5. Compute variables; run the primary test **once**.
6. Emit the full §2 report.
7. Assign the §3 outcome state.

Step 4 precedes step 5 deliberately: the sensitivity floor is a property of the
harness at that sample size and must be known before the answer is, or an
INCONCLUSIVE finding becomes unfalsifiable after the fact.

## 7. Ratified decisions

The three open points below were raised before the freeze and **ratified
2026-08-24**. They are no longer open. They are recorded here rather than
silently folded into the sections above so that the record shows what was
decided, when, and against what alternative.

### 7.1 Ratified — the reportability threshold

**Decision: the 30-event minimum applies to the TEST partition.**

Consequence, accepted: the run trigger is **≥ 30 TEST events, approximately
≥ 75 total events** at the 60/40 split — not 30 total. The literal reading
("≥ 30 events overall") was considered and rejected, because after the split it
would rest a primary out-of-sample claim on roughly twelve out-of-sample events,
which `MIN_EVENTS_FOR_REPORT` already rejects as unpowered. See §0.2 for why
that trade is worth the delay.

### 7.2 Ratified — the primary score and the model class

**Decision: the primary score is out-of-sample CRPS. The log score is a
mandatory tail-calibration diagnostic, not an optional one.**

CRPS did not exist in the research layer; the frozen research implementation scores AUC and Cohen's
d, which measure separation rather than calibration. The model class in §1.6 —
Gaussian location–scale distributional regression, ridge-penalised, λ selected
by blocked cross-validation **inside TRAIN only** — is therefore ratified as
specified, and is a decision this contract makes rather than one inherited from
existing code.

**The AUC / Cohen's-d harness is retained as a secondary diagnostic** and is
reported. It does not decide the outcome state.

Model A is the price + realised-volatility baseline (§1.4). Model B is Model A
**nested** plus the PRESAGE internals (§1.5). The split is the deterministic
60/40-by-event-index rule with a 24-hour embargo (§1.9).

Per §2.6 the log score is not merely printed: if it disagrees in sign with CRPS,
